# Phase 6 — Calling technical design (no hardware required for this doc)

Status: design only. No client dependency added, no keys provisioned, no code
wired. Implementation and all acceptance runs are queued in
`docs/DEVICE_QUEUE.md` and require two physical devices plus a LiveKit project.

## 1. Verified provider facts (checked October 2026)

- LiveKit Cloud **Build** plan: $0/mo, no credit card. Includes **5,000 WebRTC
  participant minutes/month**, **50 GB transfer**, **100 concurrent
  connections** (`docs.livekit.io`, `livekit.com/pricing`).
- Pilot math: 20 users × 100 call-minutes/month = 2,000 participant minutes —
  inside the free allowance with 2.5× headroom. Transfer at ~1 Mbps video is
  ~7.5 MB/min per direction; 2,000 minutes ≈ 15 GB — inside 50 GB.
- Verdict: free allowance **suffices for the pilot on paper**. Activation
  still requires a human to create the LiveKit project and confirm the
  allowance is actually granted (plan gate: calling stays disabled otherwise).
- Flutter SDK: `livekit_client` **2.13.0** (Aug 2026, verified publisher),
  Android/iOS/Web supported, E2EE supported (Session API simplifies setup
  since 2.9.0). Requires Flutter ≥3.38 — repo is on 3.47.5, compatible.
  Do NOT add the dependency until devices are available for testing.

## 2. Signaling (no schema change)

Call setup reuses the Phase 4 envelope transport. The JSON below travels
**inside** the Signal-encrypted message body (after base64-decoding the
decrypted `plain` bytes, parse as UTF-8 JSON; kind prefix `oc-call:`):

- `{"kind":"oc-call:invite","callId":"<uuid>","mode":"audio|video","ts":<ms>}`
- `{"kind":"oc-call:accept","callId":"<uuid>","e2eeKey":"<base64>"}`
- `{"kind":"oc-call:reject","callId":"<uuid>"}`
- `{"kind":"oc-call:end","callId":"<uuid>"}`
- Timeout: no message within 45 s of invite → caller and callee treat as missed.

`_onEnvelope` in `secure_chat_screen.dart` must attempt JSON parsing of
decrypted text and route `oc-call:*` to the call controller instead of the
message list. Text messages keep today's exact behavior.

## 3. Token endpoint (spec for the future Edge Function)

- Name: `issue-call-token`. Auth: Supabase user JWT. Params: `peer_id`, `callId`.
- Checks, in order: caller ≠ peer; `messaging_allowed(caller, peer)`
  (blocks/strangers cannot ring); pilot admission — max 10 calls/day per user
  (new `call_limits` table mirroring `message_send_limits`, or a documented
  reason to reuse it).
- Mints a LiveKit AccessToken with the API secret from function secrets:
  room `oc-<min(uuid)>-<max(uuid)>-<callId>` (per-call rooms avoid rejoin
  collisions), grant roomJoin + canPublish + canSubscribe, **TTL 30 minutes**
  (server-side max duration), metadata = caller id.
- Returns `{url, token, room, expires_at}`. Keys never ship in the client.

## 4. Media E2EE

- SFU relays ciphertext only. Per-call 256-bit key generated by the caller,
  delivered in the Signal-encrypted `accept` message (`e2eeKey`), installed
  into livekit's E2EE KeyProvider/Session API on both ends.
- Key rotation: new key per call; never reuse across calls; never log.
- Honest limit: LiveKit data-channel messages are NOT covered — signaling
  stays on our Signal transport, never the room data channel.

## 5. Client work (queued, not started)

- Add `livekit_client: ^2.13.0`; Android `CAMERA`/`RECORD_AUDIO` permissions;
  iOS usage descriptions; call screen (mute, camera switch, routing, teardown).
- `callingEnabled` flag, default false; enabled only when LiveKit URL/keys are
  present in config (mirrors the existing `config.json` pattern).
- Busy handling: one active call per pair; incoming invite during a call
  auto-rejects with `oc-call:reject`.

## 6. Acceptance mapping (requires hardware)

Two physical devices across different NATs: invite/accept/reject/timeout,
interrupt + reconnect, provider-side key invisibility (packet capture shows
ciphertext), quota cutoff (TTL expiry ends the call), and documented
force-quit behavior.
